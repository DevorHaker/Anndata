# 06 — API ARCHITECTURE & CONTRACT SPECIFICATION

## SmartProcure: REST API Domain Endpoints and Protocol Specifications

---

## 1. Global REST API Specifications

| Convention           | Standard                                                                 |
| -------------------- | ------------------------------------------------------------------------ |
| Base URL             | `/api/v1/`                                                               |
| Transport Protocol   | HTTPS / WSS                                                              |
| Data Exchange Format | JSON (`Content-Type: application/json`)                                  |
| Versioning Strategy  | URL Path Versioning (`/api/v1/`, `/api/v2/`)                             |
| Date & Time Standard | ISO 8601 UTC string (`YYYY-MM-DDTHH:mm:ss.sssZ`)                         |
| Correlation Header   | `X-Request-ID` (Generated by client or gateway, echoed in response)      |
| Idempotency Header   | `Idempotency-Key` (UUIDv4 required on resource-creating `POST` requests) |

## 3. Standard Request/Response Protocol Specifications

### 3.1 Standard Success Envelope

Every successful HTTP response returns status `200 OK`, `201 Created`, or `204 No Content` with a standard JSON envelope:

```json
{
  "success": true,
  "data": {
    "bookingId": "b8f411e2-9b24-4f32-841f-823901bc09a1",
    "status": "CONFIRMED",
    "tokenCode": "SP-9821-X"
  },
  "meta": {
    "timestamp": "2026-09-13T08:00:00.000Z",
    "requestId": "c49219b1-5e88-410a-b502-09418291a182",
    "pagination": {
      "page": 1,
      "limit": 20,
      "totalRecords": 1,
      "totalPages": 1
    }
  }
}
```

### 3.2 Standard Error Envelope

All API errors return appropriate HTTP status codes (`400`, `401`, `403`, `404`, `409`, `422`, `429`, `500`) with a structured error envelope. **Stack traces and raw database errors are strictly suppressed in production.**

```json
{
  "success": false,
  "error": {
    "code": "SLOT_FULL",
    "message": "The selected time slot has no remaining booking capacity.",
    "details": [
      {
        "field": "slotId",
        "issue": "Capacity depleted during transaction"
      }
    ],
    "requestId": "c49219b1-5e88-410a-b502-09418291a182",
    "timestamp": "2026-09-13T08:00:01.000Z"
  }
}
```

## 4. Query Parameter Standards

- **Pagination**: `GET /api/v1/bookings?page=1&limit=20` (Default limit: 20, Max: 100)
- **Sorting**: `GET /api/v1/procurements?sort=-createdAt,status` (Prefix `-` for DESC, default ASC)
- **Filtering**: `GET /api/v1/queue/centre/c123?status=WAITING&cropTypeId=cr456`
- **Search**: `GET /api/v1/farmers?search=9876543210` (Targeted search fields)

## 5. Idempotency Key Specification

To handle rural network retries safely, critical state-mutating endpoints (`POST /api/v1/bookings`, `POST /api/v1/checkins`, `POST /api/v1/procurements`) mandate an `Idempotency-Key` HTTP header.

```
Client Request -> POST /api/v1/bookings
Header -> Idempotency-Key: e827d921-1200-4b82-9e8a-782a10bc1122
```

1. Server checks Redis key `idempotency:e827d921-1200-4b82-9e8a-782a10bc1122`.
2. If key exists and status is `COMPLETED`, returns cached response payload immediately.
3. If key exists and status is `PROCESSING`, returns `409 Conflict` ("Request currently processing").
4. If key does not exist, sets key status `PROCESSING` with 24-hour TTL, executes request, caches result status `COMPLETED`, and returns response.
